## 2. Current Testing Priorities

### 2.5 No-parallel marker reduction

**Status**: **PLANNED**
**Priority**: Medium

**Goal**: Reduce `@pytest.mark.no_parallel` only when doing so does not create flakiness.

**Current rule**: Stability beats speed. Keep the marker if removing it risks false failures.

**Remaining scope (2026-11-12)**: 54 Python decorator lines across 20 test files. The two backup system-state validation tests can serve as a focused parallel check with `python -m pytest tests/behavior/test_backup_manager_behavior.py -q -n 2 -k validate_system_state`. Assess the remaining backup markers individually because those tests exercise different filesystem operations.

**Before any wave**:
- [ ] Refresh the current count:
  - `rg '@pytest.mark.no_parallel' tests/ -n`
- [ ] Identify highest-value candidates from current audit/test behavior, not from stale February lists.
- [ ] For each candidate file:
  - use unique per-test identifiers
  - isolate file writes into fixture-owned paths
  - patch shared module state/constants explicitly
  - run repeated `pytest -n auto` validation before removing the marker
  - add a reason comment if the marker remains

**Acceptance**:
- [ ] Marker count decreases only after stability evidence.
- [ ] Remaining markers have understandable reasons when practical.

**Current guidance**:

- [ ] Avoid percentage-only tests that lock in bad design or brittle implementation details.

- [ ] Revalidate the historical development-tools coverage undercount: the September 3 xdist refresh reduced the domain's statement count. Mocked checklist coverage does not establish those live outcomes. Use the [manual testing guide](../tests/MANUAL_TESTING_GUIDE.md) for these checks; do not treat them as completed by pytest.

### 2.8 Intermittent failure triage

**Status**: **MONITORING**  
**Priority**: Low/Medium

**Goal**: Keep an evidence-backed suspect queue; close resolved failures without retaining temporary instrumentation.

**Windows runner validation (2026-11-09)**

- `python run_tests.py --mode all --workers 2` passed with normal local loopback access (6,728 passed, 28 skipped). The restricted run lost `gw1` near 18% after 1,224 passes, with event-loop startup timeouts and about 86% memory usage. No failing node was captured. Restricted loopback is the working hypothesis for this recurrence.
- `python run_tests.py --mode development_tools --workers 1 --quick` passed 1,694 tests. The repaired serial phase loaded the tools configuration and completed with no eligible tests. All 21 separately selected tools slow tests passed.
- The user-run Tier 3 audit passed both tracks. The [Linux nightly](https://github.com/Jacfogel/MHM/actions/runs/42643342985) failed on one stale profile assertion. After the fix, all 33 focused profile tests passed.

**Earlier Windows evidence** — The November 6 `--mode all --full --workers 2` run lost a worker near 18% and raised an xdist rescheduling `KeyError`. Its cause remains unknown. The same run exposed the tools serial configuration error, which the November 7 isolation fix addressed. The first tools retry hit the 98% memory cutoff before the November 9 pass. See `tests/logs/backups/pytest_console_output_2026-11-06_00-31-05.txt` for the historical worker failure.

**Follow-up rules**:
- [ ] If worker loss recurs with normal loopback access, capture the active node and worker diagnostics before changing assertions or widening concurrency.
- [ ] Treat shared log/temp-path failures as harness-isolation issues first.
- [ ] Revisit `development_tools/tool_tests/test_tool_wrappers_cache_helpers.py` only if its historical intermittent failure recurs under the same execution mode.

**Status**: Planned; moved from TODO.md on 2026-11-05.
**Priority**: Low/Medium

- [ ] Establish a repeatable serial and parallel test workload with the same selected test nodes, worker count, machine, and environment.
- [ ] Record wall time, peak Python parent/worker process memory, and Windows available/cached memory before, during, and after the run. Distinguish process retention from reusable OS file cache; do not clear caches as a routine optimization.

## 4. Validation Gates

Use these gates depending on the change type.

### Audit gate (Tier 3 quick test profile)

```powershell
python development_tools/run_development_tools.py audit --full
```

Use after broad test harness, storage, command routing, scheduling, or audit-tooling changes. `audit --full` selects the full audit tier, but its default test profile is quick and excludes `slow` and `e2e` tests. An audit pass does not close the complete-suite reliability gate.

### Complete-suite reliability gate

```powershell
python run_tests.py --mode all --full --workers 1
```

This runs product and development-tools phases, including slow tests; regular runs exclude `e2e`. Use one worker while investigating the Windows failures in Section 2.8. Both parallel and serial phases must finish successfully. If the development-tools serial configuration failure recurs, repair its isolation before claiming a complete-suite pass. Live-service reload is a separate validation step.

### Targeted failing-node gate

```powershell
pytest path\to\test_file.py::TestClass::test_name -n auto
```

For flaky fixes, repeat the target several times in the same execution mode that failed.

### No-parallel conversion gate

```powershell
pytest path\to\test_file.py -n auto
```

Run after isolating shared paths/state and before removing `@pytest.mark.no_parallel`.

### Marker analysis gate

```powershell
python development_tools/tests/analyze_test_markers.py --check
```

Use when adding or reorganizing tests and after marker-policy changes.

### Coverage gate

```powershell
python development_tools/run_development_tools.py audit --full
```

The audit coverage result is scoped to its configured profile; it is not proof of a complete-suite pass. Then review:

- `development_docs/TEST_COVERAGE_REPORT.md`
- `development_tools/AI_STATUS.md`
- `development_tools/AI_PRIORITIES.md`

### Logging/isolation gate

After a test-tool or full-audit run:

- inspect `tests/logs/`
- inspect `development_tools/tests/logs/`
- confirm production logs were not polluted except the intentional dev-tools mirror
- confirm generated `tests/data/` artifacts are under expected/allowlisted roots
